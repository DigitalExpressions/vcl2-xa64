## Ownership and remaining limits

Applications use `#include "vcl2_xa64.h"`. All original root files,
`vendor/vectorclass/` and `vendor/vectorclass.json` remain byte-exact to their
existing pin. Only a separately authorized upstream update may replace them.
Do not reapply retired x86 fixes. Authoritative ARM work belongs in `_neon.h`
sources and `instrset_detect_neon.cpp`; generation remains retired.

The original x86 implementation retains valid-input issues, undefined-behavior
diagnostics, MSVC Debug RTC reports and documented contract limits. In particular,
the manual allows lookup read-ahead beyond the logical table; exact page-end
lookup tests demand a stronger guarantee. This acceptance does not endorse every
inherited difference as a documented behavior or an upstream defect. Existing
tests, stronger ARM expectations, fixtures, seeds, FP flags, sanitizer/guard
controls, 60-second deadlines and concurrency three remain unchanged.

No universal x86 correctness pass, new cross-host numerical parity, performance
gain, application integration or physical Intel coverage is claimed. A later
documentation commit or integrated tree does not inherit execution at that new
identity. The frozen source, historical reports and checksums identify the runs.

## Integration, retention and next work

Commit the reviewed portable reports and this decision above the approved
publication, then integrate into local `master` without rewriting history. Verify
protected raw hashes, dependency inventories, repository links and whitespace on
the resulting tree. This approval does not publish to a remote, create a PR or
retire any branch.

Before removing rebuildable outputs, verify original archive checksums and every
entry, inventory all cleanup candidates, record compiled hashes, and supplement
any uncovered logs, command records, diagnostic/reference inputs and generated
probe sources. Keep source captures, manifests, original archives, failures,
installed tools, pinned testbench and unrelated work. Remove the clean temporary
worktree with Git only after its source and reports are reachable from `master`.
Machine-specific coverage manifests and actual cleanup receipts stay under
ignored `build/integration-20261119-01/`; earlier dated reports remain unchanged.

The next development phase starts from this separated base and the
[ARM/Neon lessons](../neon-arm-lessons.md). First choose a bounded ARM improvement
and its numerical/API contract, preserving default sse2neon compatibility and

then freeze a new checkpoint for relevant native M2 validation. Runtime changes,
benchmarks, external consumer migration and additional publication need their
own scope; no new runtime strategy is implemented by this integration.
