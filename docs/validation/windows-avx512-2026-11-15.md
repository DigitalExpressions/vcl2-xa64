# AVX-512 fix and ARM/POSIX follow-up — 2026-11-15

This follows the [initial native Windows AMD validation](windows-amd-2026-11-15.md).
The two observed MSVC AVX-512 failures are resolved. Physical Intel testing is
omitted from this session at the user's request. Native Windows results remain
physical AMD coverage on the Ryzen 9 7950X; the additional ARM/Linux results
below run through QEMU under WSL and are identified separately.

## Reviewable local changes

All work is on `windows-native-validation`, created from `neon-port` at
`c627a2e129a2510ad9e5bb0673556456a76de346`. The source checkpoints are separated:

- `680cf45`: the previously validated Windows harness and initial results.
- `aa3836a`: the MSVC AVX-512 classification workaround and expanded regression.
- `7ac4122`: preserve GNU/Clang integer classification under finite-math flags.
- `823ca2a`: three small ARM/Linux portability corrections.

MSVC 19.44 and 19.50 emitted a 128-bit memory-broadcast FPCLASS instruction for
a 512-bit classification. The original reproducer returned `0x000f`/`0x03`
where the full masks were `0xffff`/`0xff`, including against pristine pinned
upstream. A second reproducer also exposed incomplete subnormal masks.
The workaround uses integer encodings for the five physical 512-bit
classification helpers on MSVC at instruction levels 10 and above. Clang and
other compilers retain their existing AVX512DQ path.

The regression preserves all original patterns and assertions, adds complete
mask checks at logical widths 128/256/512, and adds the small literal-broadcast
reproducer specifically for MSVC. It fails against the harness checkpoint and
passes with the workaround. Integer bits provide the independent reference;
scalar floating arguments to an oracle can acquire NaN/Inf-excluding compiler
assumptions under finite-math flags.

The expanded checks separately found Clang treating NaNs as finite in emulated
wide vectors. A compiler barrier now preserves the integer input to SSE2
`is_finite` under GNU finite-math flags, including ARM compatibility builds.
The barrier itself emits no instruction and applies only with those flags enabled.

ARM/Linux compilation exposed missing direct `<climits>` and `<cstdint>`
includes and a byte-mask array that assumed signed plain `char`. The includes
are now explicit; the array uses `int8_t`, preserving every mask byte. No
numerical reference, tolerance, generator, seed, fixture or deadline changed.

## Emulated ARM/Linux POSIX execution

An isolated Debian 13 environment in WSL supplies Clang 19.1.7, the matching
AArch64 compiler-rt, GCC 14 cross-library headers, CMake and Python. Compilation
runs on x86_64; CTest launches AArch64 ELF binaries through QEMU 8.2.8 with an
explicit ARM library root. These are emulated ARM/Linux results, not native
ARM hardware measurements. No benchmark timing was collected.

An intentional-overflow AArch64 executable demonstrated strict UBSan operation:
the positive control passed and the negative control exited 1 with the expected
overflow diagnostic. Suite instrumentation keeps
`-fsanitize=undefined -fno-sanitize-recover=undefined` and
`UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1`.

All **336 local ARM/POSIX case instances passed**, with no failures, skips,
timeouts or suite UBSan diagnostics. The complete configuration controls and
five fixture generators ran in every profile. The optional pinned upstream
ARM matrix was not repeated in this follow-up.

POSIX guard-page controls used the shared abstraction with the observed
4096-byte page size. Writable-memory controls passed; independent reads and
writes at both inaccessible boundaries each produced the expected SIGSEGV.
The regression suite retained exact boundaries, canaries and every partial
count. The Windows guard-page implementation remains covered independently.

Earlier attempts are retained as failures: Clang 14 reported unsupported
rounding behavior, and GCC 12 strict UBSan profiles reported overflow and
alignment diagnostics inside NEON intrinsic headers and failed compilation
controls. These toolchains are not counted as successful coverage. No
sanitizer checks or numerical assertions were disabled to obtain the Clang 19
results.
